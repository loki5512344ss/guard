# v0.6 — PoW: подписанный pass-токен

## Цель

Клиент решает PoW один раз и дальше предъявляет короткоживущий подписанный токен, который
любой edge проверяет без общего состояния.

## Зачем

Challenge сейчас привязан к одному TCP-соединению (`Challenge` в памяти), поэтому на HTTP
каждое новое соединение решает PoW заново, а ноды не разделяют результат. В IronShield
challenge и токен подписаны Ed25519 и несут срок жизни; сервер проверяет подпись ключом из
окружения (ключ, пришедший вместе с challenge, не доверяется). Идея подходит для
горизонтального масштабирования; код не копируем (SSPL).

## Scope

- Токен: `(ip/подсеть, expiry, difficulty)` с подписью HMAC или Ed25519, ключ из конфигурации.
- Проверка без обращения в Redis; TTL и ротация ключа.
- **Открытый вопрос:** как токен едет до PoW-гейта — гейт на уровне TCP, до HTTP. Нужен
  дизайн (PROXY-расширение, заголовок на HTTP-пути, или «recently solved» по IP).

- Для Minecraft — аналог без PoW: после первой чистой сессии кэшировать **HMAC** пары
  (username, IP) с TTL в Redis, и под атакой такие пары идут быстрым путём (идея sonar; их
  32-битный хеш для этого не годится).

## Non-goals

- Замена RST-challenge; защита от кражи токена прокси-сервером клиента (привязка к IP).

## Критерии приёмки

- [ ] Дизайн-документ с решением по транспорту токена.
- [ ] Просроченный или подделанный токен отвергается (тесты, включая чужой ключ).
- [ ] Повторное соединение с валидным токеном не получает PoW.

## Верификация

Две ноды с общим ключом: токен, выданный одной, принимает другая.
